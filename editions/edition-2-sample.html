The Algorand x402 Route Index

Edition 2 · probed 2026-09-28T08:44:06Z · USDC (ASA 31566704)

What this report is

x402 lets a web endpoint charge for each call. A client that calls without paying gets back HTTP status 402, Payment Required, together with the payment terms: the price, the asset to pay in and the address to pay. The client pays those terms and calls again.

The GoPlausible facilitator verifies and settles x402 payments on Algorand, and publishes a public directory of the endpoints that accept them. Agents and apps use that directory to find services, compare prices and choose what to call, usually before they call anything.

This report checks each listing in that directory against the endpoint itself. For every endpoint listed as accepting USDC on Algorand, it records whether the endpoint really asks for payment, which HTTP verb it asks on, and whether the price it asks is the price the directory shows.

This free report gives every figure in aggregate and names no route, payee or merchant. The full edition names them.

How we measured

  1. We read the whole directory at 2026-09-28T08:44:06Z and kept every listing priced in USDC on Algorand (asset 31566704): 2,103 endpoints.
  2. We sent each endpoint one request without payment, using the HTTP verb its listing gives. If the answer was anything other than a 402, we sent one more request with the other verb: GET or POST, whichever had not been tried. A listing that gives another verb, such as HEAD, or no verb at all, was tried with GET first. A POST carried an empty body. Redirects were followed with the same verb, up to 5 in a row.
  3. Endpoints on the same host were asked one at a time. When an endpoint answered HTTP 429, Too Many Requests, we waited as long as it asked, up to 30 seconds, and asked again with the same verb, at most 2 more times.
  4. From a 402 we read the payment terms: from its PAYMENT-REQUIRED header, or, when a 402 came without that header, from the body of the reply. From those terms we took the option for USDC on Algorand paid to the listed address, and its price.
  5. From the facilitator's public leaderboard we read the USDC it reports as settled for each endpoint and each payee address, all time, across all sources and under x402-global-challenge.
  6. For every payee address, we counted on the public Algorand indexer how many different addresses have sent it USDC.

We never paid, never sent a payment header, and never contacted a private or local network address. We read a reply's body only from a 402 that came without the header, and at most 64 KB of it. Everything here is one snapshot, taken at the time above: endpoints change, and so do prices.

What it means
An endpoint is one listed URL. A payee address is the Algorand address that receives an endpoint's payments; one merchant often runs many endpoints under one address. A host is the server name inside the URL, such as api.example.com, and many endpoints can share one.
How we measured it
Counted from the listings as the directory served them. A listing whose URL could not be read is kept exactly as served, counted as an endpoint, and not counted as a host.
Why it matters
The endpoint count alone overstates how many independent services the directory holds; the payee and host counts show how concentrated it is. The transport matters because over plain http the payment terms, and the reply that was paid for, can be read or changed on the way.
What to do
Merchants: serve every paid endpoint over https. Agents: prefer https endpoints, and skip a listing whose URL cannot be read.

What it means
  • live: the endpoint answered 402 with payment terms we could read.
  • no-402: the endpoint answered, but neither GET nor POST got a 402. It may have moved or stopped charging, or it may expect something a plain request does not send, such as query parameters.
  • unreachable: no HTTP answer at all. The name did not resolve, the connection failed or timed out, the redirects did not end, or the address was a private one we do not contact.
  • undecodable: the endpoint answered 402, but its payment terms could not be read. The header was malformed, or the body was not payment terms, was too large, was compressed, or was too slow to arrive.
  • rate-limited: the endpoint answered 429, Too Many Requests, and kept answering it after we waited and asked again. It never said whether it charges.
How we measured it
With unpaid requests as described above: the listed verb, the other verb only when the first answer was not a 402 or a 429, and a wait and a retry after a 429. Percentages are of all 2,103 endpoints.
Why it matters
An agent that picks an endpoint from the directory expects a 402 with terms it can pay. Anything other than live means the endpoint could not be paid as listed when the snapshot was taken.
What to do
Merchants: check that an unpaid request with your listed verb returns 402 with the terms, preferably in the PAYMENT-REQUIRED header, which is where clients of the current x402 protocol read them; and remove listings for endpoints you no longer run. If your endpoint is rate-limited here, check that its limit leaves room for an unpaid request followed straight away by the paid one, which is how every x402 call is made. Agents: treat a listing as a lead, and confirm it with an unpaid request before relying on it. One snapshot is not a verdict: an endpoint can be briefly down or limiting its traffic.

What it means
The listed verb is the HTTP verb the directory listing says to call the endpoint with, written as the directory wrote it. Answered to is the first verb whose unpaid request got a 402, trying the listed verb first. Once one verb got a 402 the other was not tried, so an answer on one verb does not show that the other fails.
How we measured it
As described above. The last figure counts endpoints listed as GET or POST whose listed verb got no 402 while the other verb did. Two limits: a URL listed twice under two verbs is counted once, under its first listing; and endpoints that share one URL share one pair of requests, in the order of the first listing.
Why it matters
An agent calls with the listed verb. If the endpoint charges only on the other verb, the agent gets no price and has no way to pay.
What to do
Merchants: list the verb your endpoint actually charges on. Agents: if the listed verb gets no 402, try the other one before giving up on the endpoint.

What it means
The listed price is the price in the directory listing. The live price is the price in the endpoint's own 402, for USDC on Algorand paid to the listed address. Both are per call, in USDC.
How we measured it
Compared only for endpoints that have both. How far apart two prices are is the larger divided by the smaller; a price of zero on one side counts as 10 times or more.
Why it matters
An x402 client pays the amount in the endpoint's own 402, so a payment built from that reply is still right. What goes wrong is everything decided from the directory before the call: comparing services, setting a budget, choosing what to call. And a payment prepared in advance from a directory price lower than the live price is refused.
What to do
Agents: read the price from the endpoint's 402 before committing to a call or a budget. Merchants: bring your listing back in line with what your endpoint charges.

What it means
How much USDC has settled through the GoPlausible facilitator, all time up to the snapshot, for each endpoint and for each payee address. The facilitator files every payment under a source, such as x402-global-challenge, bazaar, direct or dev; the second figure counts only the payments it filed under x402-global-challenge. The endpoint figures and the payee figures are computed separately and need not add up, in either direction: an endpoint's figure counts every payment made to that URL, whichever address received it, while the directory lists the endpoint under one payee address; a payee address's figure counts payments the leaderboard does not list endpoint by endpoint; and the lists were read seconds apart while payments kept settling.
How we measured it
Read from the facilitator's public leaderboard at the time above: endpoints matched by URL, payee addresses by address, every list read to its end. These are the facilitator's own figures, carried over unchanged and rounded to the nearest millionth of a USDC; we did not verify them. A payment on the chain carries no reference to the endpoint it paid for, so an endpoint's figure cannot be checked there. An endpoint or payee address the leaderboard does not list is left empty; one it lists, but with nothing under x402-global-challenge, shows 0 for that source.
Why it matters
A settlement count treats a call priced at a fraction of a cent and a call priced at a hundred dollars alike. Volume shows how much money actually moved.
What to do
Read it beside the settlement count and the distinct payers: many small payments from a few addresses and a few large payments from many addresses describe different kinds of use. Merchants: the facilitator records each payment's source when it settles; a figure that sits under a source you did not expect is a question for the facilitator, not something this index changes.

What it means
For each payee address, how many different Algorand addresses have ever sent it USDC.
How we measured it
From the public Algorand indexer, reading each payee address's USDC receipts page by page. It counts every USDC transfer to the address, not only x402 payments, and it belongs to the address rather than to any one endpoint. An address whose history runs past the run's page limit is left uncounted rather than given a partial number.
Why it matters
A settlement count cannot tell one wallet paying a thousand times from a thousand wallets paying once. This number can.
What to do
Read it as one sign of real use, not as a rating of quality or legitimacy: a new service naturally has few payers.

What this report does not say

There is no ranking, no score and no verdict about any endpoint or merchant. This free report names no route, payee or merchant. An empty cell always means the same thing: we tried to measure it and could not. One snapshot is not a claim that anyone's service is broken or dishonest.

Checking it yourself

Every figure on this page is computed from one file, edition-2.json, and nothing is edited by hand. Its sha256 fingerprint is the value recorded on the Algorand blockchain before anyone paid for the edition. To check that a copy is the one that was promised, compute the file's sha256 and compare the two. The manifest published beside this page, edition-2-manifest.json, lists the sha256 of this page and of every other file in the edition, so each one can be checked the same way.

The sample file published beside this page, edition-2-sample.json, carries the full edition's fingerprint as sample_of, so a buyer can confirm that these rows came out of the file they bought.
